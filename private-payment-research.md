# Private payment research candidate

Status: non-normative experiment contract, 2026-09-05. This is a bounded
candidate for testing private transfers with publicly checkable supply. It
does not amend [Construction](construction.md), define a production wire
format, or make the current transparent implementation private. An earlier
bounded run passed a real-proof issue/spend/issuer-return/burn scenario, public
replay in another process and durable receiver acceptance. The ordered-history
checkpoint fix and its valid-fork regression also passed the final real-proof
run: nine proofs, 38 named checks and eight journal tests on Windows / Node 24.

The target remains one payment product with privacy and public supply
verification together, as described in the implementation's
[production requirements](https://github.com/mediumofexchange/reference-ts/blob/main/docs/PRODUCTION_REQUIREMENTS.md).
The experiment should answer whether its proof and state-transition approach
is sound enough and practical enough to develop further. It must not become a
second production wallet or an alternative product that drops either goal.

## Scope and representations

Use Noir circuits with Poseidon2 note hashing and an actual proof backend.
Pin compiler, backend, dependencies, circuit sources, compiled artifacts,
verification keys and public-input layouts for every measured run. A successful
witness computation is not a proof. Mock proofs, a verifier returning a chosen
boolean, or signing a transparent ledger cannot satisfy the experiment.

The pool has a fixed experiment identity. Pool and asset identifiers are each
represented injectively as two unsigned 128-bit limbs of a 32-byte identifier.
For these experiments the asset identifies a particular signed backing, not a
ticker such as “EUR”. The first limb is the first 16 bytes in big-endian order;
the second is the remaining 16 bytes. Reducing an arbitrary 256-bit identifier
modulo the circuit field is not an acceptable representation. The host and
circuit check limb ranges and agree on the complete identifier.

The current runner uses signed backing objects whose **E declares transparent
evidence** as research asset/obligor mappings. Their signatures establish those
objects' identities and obligors. They do not declare or authorize this private
claim construction as the backing's conforming evidence setting. This mapping
is isolated experiment configuration; a production private profile needs an
explicit normative declaration and new corresponding signed terms.

A private note opening contains:

| Field | Constraint or purpose |
|---|---|
| Pool context | Two public u128 limbs, supplied alongside each opening |
| Asset | Two u128 limbs, bound to the same backing throughout a private transfer |
| Value | Unsigned u64 quantity of claims |
| Owner | Domain-separated hash of the receiver's spend secret |
| `rho` | Fresh cryptographic randomness generated by the wallet |

The commitment `cm` binds a note-domain tag, pool, asset, value, owner and `rho`
using the shared Poseidon2 helper. The owner hash lets a sender create an
output without learning the receiver's spend secret. Membership paths and
spend secrets are private circuit witnesses. The sender can know the opening
it constructs and can later disclose it; this is not privacy from the parties
to that payment.

The shared helper and host use these exact field-element layouts. `H` is the
experiment's Poseidon2 hash over the array shown, with its array length:

```text
owner = H([1001, secret])
cm    = H([1002, poolHi, poolLo, assetHi, assetLo, value, owner, rho])
nf    = H([1003, poolHi, poolLo, cm, secret])
node  = H([1004, level, left, right])
```

Levels run from 0 at the leaves through 7. A leaf is its commitment directly;
unused leaves are field zero. Empty parent nodes recursively use the same
level-tagged hash. A true path-direction bit means the current node is the
right child. The host encodes a field as `0x` plus exactly 64 lowercase hex
digits and rejects values outside `[0, p)`, where
`p = 21888242871839275222246405745257275088548364400416034343698204186575808495617`.
Spend secrets and freshly generated `rho` values are nonzero field elements.
These domains are specific to this research version and do not change existing
protocol hash or signature layouts.

The note tree has depth 8: at most 256 appended leaves, including zero-valued
change outputs when those are emitted. The host rejects a transition that
would exceed this capacity before changing state. There is no pruning,
rollover, historical-state migration or reuse of an old tree under the same
pool identity. This cap limits the experiment; it is not a proposed deployment
capacity.

## Three circuits, shared note rules

Each entry circuit uses the same note, owner, nullifier and tree helpers.
Keeping the three public statements distinct makes issuance and destruction
visible while leaving an ordinary transfer's asset and amount private.

| Kind | Public statement | Private witness and constraints |
|---|---|---|
| Issue | Pool, asset, issued quantity and one output `cm` | Output opening recomputes `cm` with exactly the public pool, asset and u64 quantity. The circuit proves the note relation; obligor authorization is a separate host check. |
| Spend | Pool, accepted Merkle root, input nullifier and two output commitments | Input opening, owner secret and depth-8 membership path; two output openings. Prove input membership and ownership, recompute its nullifier, and constrain both outputs to the input's pool and private asset. Their values sum exactly to the input value. Zero change is allowed. |
| Burn | Pool, accepted Merkle root, input nullifier, public asset, burned amount and change commitment | Input opening, owner secret and membership path; change opening. Bind input and change to the public pool and asset. Prove ownership, membership and nullifier derivation, with input value exactly equal to burned amount plus change value. |

The flattened public-input arrays, in verifier order, are:

```text
issue: [poolHi, poolLo, assetHi, assetLo, quantity, outputCm]
spend: [poolHi, poolLo, anchor, nf, paymentCm, changeCm]
burn:  [poolHi, poolLo, assetHi, assetLo, quantity, anchor, nf, changeCm]
```

All note values and public quantities are range-constrained u64 values.
Issuance, payment, burn quantities and authenticated input values must be
positive. Change may be zero; its commitment still occupies a leaf, and the
positive-input constraint prevents spending that zero-valued note. Output
owners, randomness and commitments must be nonzero, and a spend's two output
commitments must differ.
Conservation uses exact widened u128 arithmetic: widen before adding, then
compare. Equality in a finite field or an overflowing u64 sum does not establish
integer conservation. The circuit must constrain every public commitment to
the opening whose value participates in that equation.

The nullifier is a deterministic, domain-separated function of the immutable
input note and its owner's spend secret. It must be the same when that note is
proved against different accepted roots or paths and when it enters the spend
or burn circuit. The root and path do not enter the formula above. Keep shared
vectors and cross-circuit tests for that property.

A burn is destruction of claims. It does not prove delivery of an external
payout and cannot substitute for Construction's demand, acceptance and
holder-release redemption protocol. The scenario first transfers a note to the
issuer privately, preserving outstanding supply, then burns it in a separate
operation. This issuer-return demonstration does not implement the full private
redemption protocol or establish external performance.

## Host admission and public replay

The host fixes the expected circuit and verification key for each operation
kind. It must not accept a caller-supplied verification key, choose a circuit
by whatever happens to verify, or reinterpret one public-input vector as
another operation kind. Verify proof bytes against the exact public statement
that will be checked, persisted and replayed.

For issue, validate the signed backing and its obligor's signature authorizing
this experiment's pool, asset, quantity and output commitment under an explicit
issuance domain/version. The signature must authorize those exact public
inputs. A signature over the backing terms alone does not authorize issuing
an arbitrary quantity. Commitment uniqueness supplies a replay identity for
that issuance; replay must not append it or increase supply again.

The host's research profile is `moe-private-payment-research/v1`. Its SHA-256
configuration identity hashes the raw UTF-8 context `PROFILE + "/config"`,
the two pool limbs as 32-byte big-endian fields, bytecode and verification-key
SHA-256 digests in `issue`, `spend`, `burn` order, then a big-endian u32 asset
count. Assets are sorted by their 32-byte hexadecimal identifier; each record
contains that identifier, u32-length-prefixed encoded terms, and a 64-byte
backing signature. The signed issuance statement is the raw UTF-8 context
`PROFILE + "/statement"`, the 32-byte configuration hash, a u8 kind code
(`issue=1`, `spend=2`, `burn=3`), a big-endian u32 public-input count, then each
public input as a 32-byte big-endian field. The obligor signs these exact bytes
with the existing strict Ed25519 signature primitive. JSON envelopes are not
the signed encoding. Both contexts and their layouts are research-only.

Before a valid proof changes state, the host must establish all of the
following against one transactional view:

1. The pool and asset binding are appropriate for this operation and supported
   signed terms. Circuit kind and public-input layout match the pinned record.
2. A spend or burn root is an accepted root from this pool's prior history.
   Mathematical membership under a caller-invented root is insufficient.
3. The input nullifier has not occurred anywhere in the pool's accepted spend
   or burn history. One shared nullifier set covers both operation kinds and
   every retained anchor.
4. Every output commitment is new to the pool, outputs are distinct from each
   other, and the complete append fits within the tree capacity.
5. The verified proof/public inputs and required issuance authorization are
   persisted with the resulting ordered transition, roots and accounting
   changes. Nullifier insertion, output insertion and supply updates commit
   together before an accepted response escapes.

The implementation verifies proofs and computes the candidate transition from
a journal snapshot outside SQLite transactions. Its conditional append compares
the snapshot sequence with the current journal tip under `BEGIN IMMEDIATE`;
if another writer advanced it, the host reloads, replays and recomputes all
mutable checks before retrying. This binds the checks to the admitted state
without holding the writer lock during asynchronous proving or verification.
Concurrent valid proofs spending the same input must never both be accepted.
An exact retry returns its existing result; conflicting replay is rejected.
A failed proof or state check leaves no partial insertion, burn or issuance.

Public operator records contain proof bytes, public inputs, authorization
evidence where needed and the ordered state changes. They must not contain
spend secrets, input openings, private assets/values from a spend, membership
paths or receiver recovery plaintext. Passing private inputs to the operator
so it can regenerate a proof defeats the experiment's separation of roles.

An independent verifier replays the actual published proofs and the same
admission rules from the initial state. For every public issuance and burn it
checks the authorization and accounting boundary; for private spends it checks
same-asset conservation without knowing the asset or value. Supply is thus
derived per backing from verified issuance minus verified burns, not from an
operator's asserted aggregate. Missing evidence needed by a supplied transition
prevents its verification. **A valid earlier prefix can still replay
successfully after later transactions have been withheld.** Replay therefore
proves only the supplied prefix, not freshness, current supply, or an independently
final history. The experiment supplies neither an independent finality witness
nor a guarantee that all public evidence remains available.

## Ordered history checkpoints

A note-tree root and transition count do not bind the spent set. Two valid
histories can spend different equal-valued notes owned by the prover and append
the same output commitments. Their note roots and counts match while their
nullifiers differ. Accepting either history against only that root/count pair
would leave the claimed unspentness ambiguous.

The host now hashes the ordered public statements as well as the resulting
note roots. With `PROFILE = "moe-private-payment-research/v1"`, the exact
SHA-256 input layouts are:

```text
historyHash_0 = SHA256(
  UTF8(PROFILE + "/history/genesis") || configHash32
)
statementHash_i = SHA256(statementBytes_i)
historyHash_i = SHA256(
  UTF8(PROFILE + "/history") || historyHash_(i-1)32 ||
  statementHash_i32 || noteRoot_i32 || u64be(i)
)
```

Contexts are written raw; each named hash/root occupies exactly 32 bytes and
the count occupies eight big-endian bytes. The root uses its canonical field
value as 32 big-endian bytes. `statementBytes` is the framed statement defined
above, binding configuration, operation kind and public inputs, including the
nullifier. The genesis hash binds the configuration even for an empty history.
These hashes bind accepted statements and their order, not randomized proof
bytes; replay must still verify the actual proofs and issuance authorization.

Each durable response now carries `{sequence, statement, root, historyHash}`.
The audit caller supplies the expected `{root, count, historyHash}` separately
from the untrusted history, and the audit compares all three after replay.
Taking the expected checkpoint from the same untrusted file would defeat this
check. The new regression constructs both valid branches described above,
confirms equal roots/counts and different spent sets, and requires a separate
auditor to reject one branch against the other's history hash. That regression
passed the revised real-proof run, with actual verification on both branches.

A pinned ordered hash identifies the caller's expected history. It does not
establish that this history is current, globally agreed, independently
witnessed or continuously available. A valid prefix still replays on its own;
it is rejected as a substitute only when a separately supplied expected
checkpoint identifies a different history. The production source and freshness
of such a checkpoint remain unresolved.

## Receiver acceptance

The payer supplies the receiver's output opening through a private channel.
The receiver independently checks its owner value, expected pool, asset and
quantity; recomputes the output commitment; and verifies that exact commitment
occurs among the accepted transition's outputs. The implemented check also
rejects a note whose nullifier appears in the supplied prefix. It retains the opening and
whatever authenticated history it needs to spend later. A valid proof for some
other output is not evidence that this receiver was paid.

The receiver persists acceptance of the output commitment before crediting it
or triggering a side effect. Restarting or receiving the proof twice must not
credit it twice. Binding a payment to a fresh purchase, safely backing up note
openings and implementing application fulfillment remain separate obligations;
accept-once output storage alone is not a complete merchant wallet. This is
acceptance relative to a locally supplied history: a withheld suffix can hide
a later spend. It does not prove current unspentness or independent finality.

## What remains visible and trusted

Ordinary spend statements reveal an anchor, a nullifier, two new commitments,
proof shape and timing. They aim to hide which input leaf was spent, the asset,
amounts and recipient ownership from observers lacking the openings and
secrets. Issue reveals asset and quantity; burn reveals asset and quantity.
These public boundaries can allow inference, especially in a small pool.

The experiment does not provide anonymous transport, traffic shaping, batching,
receiver discovery, encrypted note delivery, metadata-safe backups or a large
anonymity set. IP addresses, timing, output order, wallet behavior and disclosed
openings can link parties. Sender/receiver collusion and collusion with issuers,
operators or witnesses need explicit analysis. Zero-valued change does not
itself create cover traffic or anonymity. No measured circuit result can
establish protection from those channels.

The local host still orders and retains history. Replaying its proofs does not
make its clock independent, stop it withholding data or resolve competing valid
histories. The proof backend, cryptographic assumptions and any setup material
are part of the research trust model and must be stated with the pinned run.

## Evidence and promotion blockers

An experiment result must include generated proofs for issue → spend → burn,
independent proof verification and public replay, and receiver accept-once
behavior across restart. Negative cases must cover wrong ownership, changed
pool/asset/quantity/output, invalid paths, unknown anchors, duplicate
commitments/nullifiers, cross-kind and cross-anchor double spends, integer
range/overflow, invalid issuance signatures, proof/public-input tampering,
wrong verification keys and full-tree admission. Report the cases actually run
and their outcomes; this document is not a claim that they already pass.

Measure compilation, witness computation, proving, verification, proof size,
public-record growth and peak memory separately. Record hardware, operating
system, Node.js 24 version, toolchain versions, warm/cold conditions and
repeated-run results. Desktop measurements are desktop evidence. They establish
neither mobile usability nor production throughput.

Promotion requires independent circuit/host review, a precise production
privacy and collusion model, measured supported devices, scalable state and
resynchronization, protected keys and backups, private note delivery,
independent witnessing and availability, and a specified recovery/redemption
path. The capacity cap and one-input/two-output shape leave aggregation and
long-lived operation unresolved. No production release follows merely from
valid proofs or a passing demonstration.

If this candidate survives those checks, propose the selected construction and
its migration rules in Construction before integrating it into the single
product path. Preserve useful vectors and adversarial cases, then retire
superseded experiment entry points. Existing transparent protocol signatures,
runtime encodings and deployment claims remain unchanged by this document.
